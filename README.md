# Ranenla Backend

API for the Ranenla / Nexora platform — **Node.js + Express + TypeScript**, **PostgreSQL** via **Prisma**.

This repo is currently a **structure-only scaffold**: folders and placeholder files with
`// TODO` comments, no business logic yet. It exists so every contributor builds features
in the same shape from day one. Read this whole file before writing your first module.

## Stack

| Layer      | Choice                          |
| ---------- | -------------------------------- |
| Runtime    | Node.js 20+, TypeScript          |
| Web        | Express 5                        |
| Database   | PostgreSQL                       |
| ORM        | Prisma                           |
| Lint/format| ESLint (flat config) + Prettier  |

## Getting started

```bash
npm install
cp .env.example .env        # fill in DATABASE_URL, JWT_SECRET, ...
npm run prisma:generate
npm run prisma:migrate      # once models exist in prisma/schema.prisma
npm run dev                 # starts the API with hot reload
```

## Architecture: request flow

Every request flows through the same four layers, in the same direction. Each layer only
ever talks to the one directly below it.

```
routes  ->  controllers  ->  services  ->  repositories  ->  Prisma  ->  PostgreSQL
```

| Layer            | Responsibility                                                              | Must NOT do                              |
| ----------------- | ---------------------------------------------------------------------------- | ----------------------------------------- |
| **routes**        | Map `verb + path` to a controller method, attach middleware.                 | Business logic, DB access                 |
| **controllers**   | Read `req`, call one service method, shape the `res` (status + JSON).        | Business logic, Prisma calls              |
| **services**      | Business logic, validation rules, orchestration across repositories.         | Touch `req`/`res`, import Prisma directly |
| **repositories**  | One Prisma call per method (`findMany`, `create`, `update`, ...). Nothing else. | Business rules, conditionals beyond query filters |

Supporting folders that sit alongside this pipeline:

- **`middlewares/`** — cross-cutting concerns (auth, validation, error handling) attached at
  the route level.
- **`validators/`** — request payload schemas, run as middleware before a controller ever
  sees the request.
- **`config/`** — env loading and the shared Prisma client singleton.
- **`utils/`** — small stateless helpers (`ApiError`, `asyncHandler`, `logger`) used across
  modules.
- **`types/`** — shared TypeScript types and Express type augmentation.

### Do we need a repository layer?

**Yes — keep it, but keep it thin.** Prisma Client already *is* a data-access layer, so the
repository here isn't hiding SQL — it's a 1:1 wrapper per model. The payoff for a team of
interns:

- **One place per model for queries.** If the `User` query logic needs to change (a new
  `include`, a soft-delete filter), it changes in one file instead of every service that
  touched `prisma.user.*`.
- **Services stay testable.** Mock the repository, test business logic without a real
  database.
- **A clear line for code review.** "Is this a query or a business rule?" maps directly to
  "repository or service?" — useful when reviewing intern PRs.
- **Swappable later.** Unlikely to happen, but if the ORM ever changes, only the repository
  layer is rewritten.

The cost is a bit of boilerplate (an extra file per module), which is worth it here because
consistency across many contributors matters more than saving a few lines.

## Adding a new module

The `user` module in every folder above is the template — it's intentionally empty
(`// TODO` comments only) but shows the exact file set and naming pattern. To add a new
module called `<name>` (e.g. `course`, `assignment`, `attendance`):

1. Add the model(s) to `prisma/schema.prisma`, then run `npm run prisma:migrate`.
2. Create one file per layer, following the `user.*` naming:
   - `src/repositories/<name>.repository.ts`
   - `src/services/<name>.service.ts`
   - `src/validators/<name>.validator.ts`
   - `src/controllers/<name>.controller.ts`
   - `src/routes/<name>.routes.ts`
3. Register the new router in `src/routes/index.ts`.
4. Add `tests/<name>.test.ts`.

Suggested first modules, matching the frontend's existing screens: `auth`, `user`, `course`,
`assignment`, `attendance`, `achievement`, `message`, `live-class`, `progress`.

## Conventions

- **Naming:** `<module>.<layer>.ts` everywhere (`course.controller.ts`, not `CourseController.ts`).
- **No Prisma outside repositories.** If you're tempted to `import { prisma }` in a service
  or controller, add a repository method instead.
- **No `req`/`res` outside controllers.** Services take/return plain data so they're reusable
  (e.g. from a script or a queue worker) and unit-testable without mocking Express.
- **Errors:** throw `ApiError(statusCode, message)` from any layer; let it bubble to
  `error.middleware.ts` rather than handling it locally.
- **Env vars:** add new ones to `.env.example` (with a placeholder/empty value) whenever you
  add one to `.env`.
- **Branches/PRs:** one module (or one clearly-scoped slice of a module) per PR, so reviews
  stay small.

## Scripts

| ------------------------- | ---------------------------------------------- |
| `npm run dev`             | Start the API with hot reload (`tsx watch`)    |
| `npm run build`           | Compile TypeScript to `dist/`                  |

| `npm run prisma:generate` | Regenerate the Prisma client                   |
| `npm run prisma:migrate`  | Create + apply a dev migration                 |
